任何模块都要自独立、分布式

包括配置，这里的配置要想个办法，可以支持通信获取配置

因为未来系统变大之后必然要拆分的很细，每一个小的模块也可能随着业务复杂而变大庞大

可选配置项目抽离、与业务逻辑分离

我可以封装一个宏定义去导出一些固定规则的函数接口，这些函数接口通过宏定义导出到一个链表中，这个链表会创建heap加入list，然后在程序的初始化或者mainfunction中去周期调用

所以我可以单独的把每一个实现逻辑给实现，然后再一个另外的一个层级去组织这些逻辑关系的函数调用，接着呢，可以用一些描述的方式去组织不同的逻辑之间的如何依赖或者执行调用这些

对外的状态通知可以做一个专门的模块处理这个事情，有变动的时候就交给这个模块去处理

也就是说每个模块都共有的特性，可以抽出来一个专门的模块去处理，比如 log，status，object等等

单独的测试管理模块，所有的服务导出一个测试用例，这里会通过测试模块进行运行管理，最后输出测试报告

一个窗口的界面系统，这里负责管理与用户交互的界面，与每个模块都有对应的设定

集群，可以通过一些规则，随机延迟啊，ping的速度呀，进行打分，然后选举出谁作为主节点
为了避免脑裂现象，也就是说集群中有一批人无法通信导致出现了两个子集群，所以投票数需要超过总数的一半

设计时要把代码划分为变化的部分和不变的部分，做到分离

要有抽象层和实现层

C语言的状态switch中可以抽象出来一个统一的接口函数来做分离，这时，状态切换可以加入各种回调接口，比如log，状态通知等等
枚举尽量用位来表示，这样可以一个实体同时有多种枚举属性，代码更加精简
